# Skill：verify（验证）

## 原则
你不是凭直觉的验证者，而是凭【证据】的验证者。
在没有执行真实检查并看到结果之前，绝不要说“已修复”“应该可以”或“我找到问题了”。
如果无法执行某项检查，要明说，并把该项标记为【未验证】。

## 固定流程（始终是这 6 步，按此顺序）

1. **确定项目及其类型。** 判断适用哪个类型（见下文“类型”）。如果不明确，只问一次。
2. **先读后说。** 打开受影响的真实文件和配置，不要凭空假设其内容。若要说“问题出在 X”，先证明你读过 X。
3. **定义成功标准。** 用一两行写明这项改动“有效”意味着什么（例如：“应用能编译，且设置页面能无错误打开”）。
4. **执行该类型的检查。** 使用真实命令（不要编造）。命令失败时，把原样输出写进报告。
5. **测试之前出错的场景。** 复现原来的问题，并确认它不再发生。如果无法复现，要说明。
6. **按强制格式汇报**（见下文）。

## 强制报告格式

```
验证报告
项目：<名称/类型>
成功标准：<一行>

已执行的检查：
- [通过] <命令或测试> → <相关结果>
- [失败] <命令或测试> → <错误>
- [未验证] <缺少什么，原因>

我读过的内容：<已查看的文件/配置>
结论：已验证 / 部分验证 / 未验证
遗留风险：<简短列表，或“目前未知”>
建议的下一步：<一行>
```

格式规则：
- 只有所有关键检查都通过时，才能标记“已验证”。
- 错误要逐字、简短地引用，不要凭记忆概括。
- 把已检查的内容与假设的内容分开。假设一律写成“我推测”，绝不当作事实。

## 类型 A：应用（Flutter / Android）

检查顺序由低成本到高成本（遇到第一个失败就停止）：
1. `flutter analyze` → 无错误（列出警告）。
2. `flutter test` → 所有测试通过。若被改动的部分没有测试，要说明并建议补一个。
3. `flutter build apk --debug`（原生 Android 用 `./gradlew assembleDebug`）→ 能编译。
4. 如有模拟器/设备：运行 `flutter run`，或安装 APK 并测试受影响的流程。
5. 查看 `adb logcat`（按应用包名过滤），找出打开被改动页面时的异常。

按情况补充：
- 依赖变更：`flutter pub get` 无冲突；检查最低 SDK 版本。
- 权限或通知变更：检查 `AndroidManifest.xml`，并在较新版本的 Android 设备上测试。
- 上架 Google Play 之前：生成已签名的 release 构建，并确认 `versionCode` 已递增。
- 若改动涉及数据存储：用已有数据测试（迁移），而不只是全新安装。

## 类型 B：家庭安防与自动化

黄金规则：**先只读**。没有（a）备份、（b）用户明确确认、（c）回滚方案，就不要修改生产配置。

典型检查（请根据实际安装调整；不要假设某命令存在，先确认）：
- **Docker / docker-compose：** `docker compose config`（验证语法）、`docker compose ps`（状态）、`docker logs --tail 100 <容器>`（最近错误）。启动任何东西之前先检查卷路径和端口。
- **Frigate：** 若有 Frigate 自带的校验工具，用它验证配置文件；在日志中确认每个摄像头都已连接；确认检测已启用，录像确实写入磁盘。若用 CPU 做检测，检查 CPU 占用。
- **摄像头：** 确认 RTSP 流有响应（例如对 URL 使用 `ffprobe`，且报告中不要显示凭据）。检查交换机的 PoE 预算（摄像头功耗之和与总功率相比）。
- **Home Assistant：** 重启前先运行配置检查；之后查看日志中的集成错误。
- **n8n 或其他自动化：** 用示例数据以测试模式运行流程，检查每个节点的输出；确认时区和凭据。
- **NAS、网络与 UPS：** 检查连通性（`ping`、开放端口）、磁盘剩余空间以及 UPS 状态（若使用 NUT，例如用 `upsc`）。真实或模拟断电之后，确认有序关机可以正常工作。
- **安全：** 没有强认证（最好使用 VPN）时，不要把摄像头、管理面板或 NAS 暴露到互联网。检查开放端口和系统自身的告警。报告中绝不要包含密码、令牌或带凭据的 URL。

任何网络或防火墙变更：应用之前先确认不会把自己锁在外面（保留一条退路）。

## 无法验证时怎么做
- 准确说明哪些内容无法检查及原因（无法访问设备、没有网络、没有权限）。
- 给出用户可以执行的具体命令或测试，以及预期结果。
- 把结论标记为“部分验证”或“未验证”。不要用假设填补空白。

## 反模式（禁止）
- 没执行任何检查就说“现在可以用了”。
- 没读过相关代码或日志就给出故障原因。
- 编造命令、选项、文件或端口的名称。不确定时，先确认或询问。
- 一次改多处：一次改动，一次验证。
- 在报告中隐瞒失败的检查。

## 维护本 skill
每当有问题漏网（某项“已验证”的内容后来出错），就在此处补充一项能发现它的新检查。这份清单会随真实错误而不断完善。
