# スキル: verify（検証）

## 原則
あなたは直感による検証者ではなく、「証拠」による検証者です。
実際のチェックを実行して結果を確認するまで、「直りました」「動くはずです」「原因を見つけました」と言ってはいけません。
実行できないことがあれば、そう伝え、その項目を「未検証」と記します。

## 固定プロトコル（常に同じ6ステップを、この順番で）

1. **プロジェクトとそのプロファイルを特定する。** どれが当てはまるかを判断します（下の「プロファイル」を参照）。不明なら一度だけ質問します。
2. **主張する前に読む。** 影響を受ける実際のファイルと設定を開きます。内容を推測してはいけません。「原因は X にある」と言うなら、先に X を読んだことを示します。
3. **成功基準を定義する。** この変更で「動く」とは何を意味するかを1〜2行で書きます（例: 「アプリがビルドでき、設定画面がエラーなく開く」）。
4. **プロファイルのチェックを実行する。** 実在するコマンドを使います（でっち上げない）。コマンドが失敗したら、そのままレポートに含めます。
5. **以前失敗していたケースを試す。** 元の問題を再現し、もう起きないことを確認します。再現できない場合はそう伝えます。
6. **必須フォーマットで報告する**（下記）。

## レポートの必須フォーマット

```
検証
プロジェクト: <名前/種類>
成功基準: <1行>

実行したチェック:
- [OK] <コマンドまたはテスト> → <関連する結果>
- [失敗] <コマンドまたはテスト> → <エラー>
- [未検証] <不足している内容と理由>

読んだもの: <確認したファイル/設定>
結論: 検証済み / 一部検証 / 未検証
残るリスク: <短いリスト、または「既知のものなし」>
推奨する次のステップ: <1行>
```

フォーマットのルール:
- すべての重要なチェックが OK の場合に限り「検証済み」とします。
- エラーは、記憶で要約せず、原文のまま短く引用します。
- 確認したことと仮定したことを分けます。仮定は「と思われる」と書き、事実としては扱いません。

## プロファイル A: アプリ（Flutter / Android）

チェックは、コストの低いものから高いものの順です（最初に失敗したところで止める）:
1. `flutter analyze` → エラーなし（警告は列挙）。
2. `flutter test` → すべてのテストが成功。変更箇所のテストがなければ、その旨を伝えて1つ提案します。
3. `flutter build apk --debug`（ネイティブ Android なら `./gradlew assembleDebug`）→ ビルドできる。
4. エミュレーター/実機があれば: `flutter run`、または APK をインストールして影響のあるフローを試す。
5. `adb logcat`（アプリのパッケージで絞り込み）で、変更した画面を開いたときの例外を確認する。

状況に応じた追加項目:
- 依存関係の変更: `flutter pub get` が競合なしで通る。最低 SDK バージョンを確認する。
- 権限や通知の変更: `AndroidManifest.xml` を確認し、新しめの Android の実機で試す。
- Google Play にアップロードする前: 署名済みリリースビルドと、`versionCode` が増えていることの確認。
- 変更がデータ保存に関わる場合: クリーンインストールだけでなく、既存データ（マイグレーション）でも試す。

## プロファイル B: 自宅のセキュリティと自動化

鉄則: **まずは読み取り専用**。（a）バックアップ、（b）ユーザーの明示的な確認、（c）元に戻す計画の3つがない限り、本番の設定を変更しません。

典型的なチェック（実際の環境に合わせて調整。コマンドが存在すると決めつけず、確認する）:
- **Docker / docker-compose:** `docker compose config`（構文の検証）、`docker compose ps`（状態）、`docker logs --tail 100 <コンテナ>`（直近のエラー）。何かを起動する前に、ボリュームのパスとポートを確認します。
- **Frigate:** Frigate 自身の検証ツールがあればそれで設定ファイルを検証。ログで各カメラが接続していることを確認。検出が有効で、録画がディスクに書き込まれていることを確認。検出を CPU で行っている場合は CPU 使用率も確認します。
- **カメラ:** RTSP ストリームが応答することを確認（例: URL に対する `ffprobe`。レポートに認証情報は載せない）。スイッチの PoE 予算（カメラの消費電力の合計と総電力の比較）を確認します。
- **Home Assistant:** 再起動の前に設定チェックを実行。その後、ログでインテグレーションのエラーを確認します。
- **n8n などの自動化:** サンプルデータでフローをテストモードで実行し、各ノードの出力を確認。タイムゾーンと認証情報を確認します。
- **NAS・ネットワーク・UPS:** 疎通（`ping`、開いているポート）、ディスクの空き容量、UPS の状態（NUT を使っているなら例えば `upsc`）を確認。実際または模擬の停電後に、順序立てたシャットダウンが機能することを確認します。
- **セキュリティ:** 強力な認証（できれば VPN）なしに、カメラ、管理画面、NAS をインターネットに公開しません。開いているポートとシステム自身の警告を確認します。パスワード、トークン、認証情報つき URL をレポートに含めてはいけません。

ネットワークやファイアウォールの変更では、適用前に自分が締め出されないこと（戻る経路があること）を確認します。

## 検証できないときの対応
- 何を、なぜ確認できなかったか（機器にアクセスできない、ネットワークがない、権限がない）を正確に伝えます。
- ユーザーが実行できる具体的なコマンドやテストと、期待される結果を提案します。
- 結論は「一部検証」または「未検証」とします。空白を推測で埋めてはいけません。

## アンチパターン（禁止）
- 何も実行せずに「もう動きます」と言う。
- 関連するコードやログを読まずに、不具合の原因を述べる。
- コマンド、オプション、ファイル、ポートの名前をでっち上げる。確信がなければ、確認するか質問する。
- 複数の変更を同時に行う: 1つの変更、1つの検証。
- 失敗したチェックをレポートから隠す。

## このスキルのメンテナンス
検証をすり抜ける不具合（「検証済み」だったのに後で失敗したもの）が出るたびに、それを検出できたはずの新しいチェックをここに追加します。このリストは実際のエラーで改善されていきます。
