# 스킬: verify (검증)

## 원칙
당신은 직감으로 검증하는 사람이 아니라 '증거'로 검증하는 사람입니다.
실제 점검을 실행하고 그 결과를 확인하기 전에는 "고쳤습니다", "될 겁니다", "문제를 찾았습니다"라고 말하지 마세요.
무언가를 실행할 수 없다면 그렇게 말하고, 해당 항목을 '검증 안 됨'으로 표시하세요.

## 고정 절차 (항상 같은 6단계, 이 순서대로)

1. **프로젝트와 프로필을 파악합니다.** 어느 것이 해당하는지 판단합니다(아래 "프로필" 참조). 불분명하면 한 번만 물어보세요.
2. **주장하기 전에 읽습니다.** 영향을 받는 실제 파일과 설정을 엽니다. 내용을 추측하지 마세요. "문제는 X에 있다"고 말하려면 먼저 X를 읽었다는 것을 보여 주세요.
3. **성공 기준을 정의합니다.** 이번 변경에서 "동작한다"가 무엇을 뜻하는지 한두 줄로 적습니다(예: "앱이 빌드되고 설정 화면이 오류 없이 열린다").
4. **프로필의 점검을 실행합니다.** 실제 명령을 사용하세요(지어내지 않기). 명령이 실패하면 보고서에 그대로 포함합니다.
5. **전에 실패하던 경우를 시험합니다.** 원래 문제를 재현하고 더 이상 발생하지 않음을 확인합니다. 재현할 수 없다면 그렇게 말합니다.
6. **필수 형식으로 보고합니다**(아래 참조).

## 보고서 필수 형식

```
검증
프로젝트: <이름/유형>
성공 기준: <한 줄>

실행한 점검:
- [통과] <명령 또는 테스트> → <관련 결과>
- [실패] <명령 또는 테스트> → <오류>
- [검증 안 됨] <무엇이 부족하며 이유는 무엇인지>

읽은 것: <확인한 파일/설정>
결론: 검증됨 / 부분 검증 / 검증 안 됨
남은 위험: <짧은 목록 또는 "알려진 것 없음">
권장하는 다음 단계: <한 줄>
```

형식 규칙:
- 모든 핵심 점검이 통과한 경우에만 '검증됨'으로 표시합니다.
- 오류는 기억으로 요약하지 말고, 원문 그대로 짧게 인용합니다.
- 확인한 것과 가정한 것을 구분합니다. 가정은 "추정합니다"로 쓰고, 사실로 쓰지 않습니다.

## 프로필 A: 앱 (Flutter / Android)

비용이 적은 점검부터 큰 점검 순서로 합니다(처음 실패한 곳에서 멈춤):
1. `flutter analyze` → 오류 없음(경고는 나열).
2. `flutter test` → 모든 테스트 통과. 바뀐 부분에 테스트가 없다면 그렇게 말하고 하나 제안합니다.
3. `flutter build apk --debug`(네이티브 Android는 `./gradlew assembleDebug`) → 빌드됨.
4. 에뮬레이터/기기가 있다면: `flutter run` 또는 APK를 설치하여 영향받는 흐름을 시험합니다.
5. `adb logcat`(앱 패키지로 필터링)에서 수정한 화면을 열 때의 예외를 확인합니다.

상황에 따른 추가 사항:
- 의존성 변경: `flutter pub get`이 충돌 없이 완료됨. 최소 SDK 버전을 확인합니다.
- 권한 또는 알림 변경: `AndroidManifest.xml`을 검토하고 최신 Android 기기에서 시험합니다.
- Google Play에 올리기 전: 서명된 릴리스 빌드와 `versionCode`가 올라갔는지 확인합니다.
- 변경이 데이터 저장과 관련된 경우: 새로 설치한 경우만이 아니라 기존 데이터(마이그레이션)로도 시험합니다.

## 프로필 B: 홈 보안과 자동화

황금률: **먼저 읽기 전용으로.** (a) 백업, (b) 사용자의 명시적 확인, (c) 되돌리기 계획이 없으면 운영 설정을 변경하지 않습니다.

대표적인 점검(실제 설치 환경에 맞추세요. 명령이 존재한다고 가정하지 말고 확인하세요):
- **Docker / docker-compose:** `docker compose config`(문법 검증), `docker compose ps`(상태), `docker logs --tail 100 <컨테이너>`(최근 오류). 무언가를 띄우기 전에 볼륨 경로와 포트를 검토합니다.
- **Frigate:** Frigate 자체 도구가 있으면 그것으로 설정 파일을 검증합니다. 로그에서 각 카메라가 연결되는지 확인합니다. 감지가 활성화되어 있고 녹화가 디스크에 기록되는지 확인합니다. 감지를 CPU로 한다면 CPU 사용률을 확인합니다.
- **카메라:** RTSP 스트림이 응답하는지 확인합니다(예: URL에 `ffprobe`. 보고서에 자격 증명을 노출하지 않음). 스위치의 PoE 예산(카메라 소비 전력 합계 대 총 전력)을 검토합니다.
- **Home Assistant:** 재시작 전에 설정 점검을 실행합니다. 이후 로그에서 통합(integration) 오류를 확인합니다.
- **n8n 등 자동화:** 예시 데이터로 테스트 모드에서 플로를 실행하고 각 노드의 출력을 확인합니다. 시간대와 자격 증명을 확인합니다.
- **NAS, 네트워크, UPS:** 연결성(`ping`, 열린 포트), 디스크 여유 공간, UPS 상태(NUT를 쓰면 예: `upsc`)를 확인합니다. 실제 또는 모의 정전 후 순차 종료가 작동하는지 확인합니다.
- **보안:** 강력한 인증(가능하면 VPN) 없이 카메라, 관리 화면, NAS를 인터넷에 노출하지 않습니다. 열린 포트와 시스템 자체 경고를 검토합니다. 보고서에 비밀번호, 토큰, 자격 증명이 포함된 URL을 절대 넣지 않습니다.

네트워크나 방화벽을 변경할 때는 적용 전에 스스로 접속이 막히지 않는지(되돌아갈 길이 있는지) 확인합니다.

## 검증할 수 없을 때
- 무엇을 왜 확인하지 못했는지(기기에 접근 불가, 네트워크 없음, 권한 없음) 정확히 말합니다.
- 사용자가 실행할 수 있는 구체적인 명령이나 테스트와 기대 결과를 제안합니다.
- 결론을 '부분 검증' 또는 '검증 안 됨'으로 표시합니다. 빈틈을 추측으로 채우지 않습니다.

## 안티패턴 (금지)
- 아무것도 실행하지 않고 "이제 됩니다"라고 말하기.
- 관련 코드나 로그를 읽지 않고 실패 원인을 말하기.
- 명령, 옵션, 파일, 포트 이름을 지어내기. 확실하지 않으면 확인하거나 물어보기.
- 여러 가지를 한꺼번에 바꾸기: 변경 하나, 검증 하나.
- 실패한 점검을 보고서에서 숨기기.

## 이 스킬의 유지 관리
검증을 빠져나간 문제(검증됨이었는데 나중에 실패한 것)가 생길 때마다, 그것을 잡아냈을 새 점검을 여기에 추가하세요. 이 목록은 실제 오류로 개선됩니다.
